RabbitMQ Study Notes: Use Cases, Core Concepts and Reliability ​

Notes from working through RabbitMQ: what a message queue actually buys you, how the pieces fit together, and how to keep messages from getting lost.

1. Use cases ​

1.1 Decoupling ​

A typical business flow looks like this: purchase → generate a receipt → send an SMS. But generating the receipt and the SMS are not necessary services. If either of them fails, the payment service gets stuck. A message queue solves exactly this problem.

A queue is more like a courier station: the merchant drops the parcel off and is no longer responsible for it — the courier only has to make sure the message reaches the recipient.

So with a queue the system responds to the user faster, and a failure in the receipt or message module no longer drags down the payment system.

1.2 Traffic shaping ​

Normally users send requests straight to the system. But if too many users hit the same part at the same moment, the system can crash — and the requests it had not processed yet are lost.

With a queue, the queue holds the users' requests. Even if the system crashes, the data in the queue is not lost, and the queue acts as a buffer for the system.

2. How RabbitMQ works ​

  • Broker — provides the transport service; its role is to maintain the route from producer to consumer and to make sure data is delivered the way it was specified. (The broker is the RabbitMQ server.)
  • Exchange — the message switch: it decides by which rule messages are routed to which queue.
  • Queue — the carrier of messages; every message is delivered to one or more queues.
  • Binding — binds an exchange and a queue together according to routing rules.
  • Routing key — the routing keyword the exchange uses to deliver messages.
  • vhost — virtual host; one broker can hold several vhosts, used to separate the permissions of different users.
  • Producer — the program that publishes messages.
  • Consumer — the program that receives messages.
  • Channel — the message channel; several channels can be created inside each client connection.

3. Exchanges ​

RabbitMQ has several kinds of exchange.

Direct ​

A direct exchange is one-to-one: the client carries a routing key, and the exchange sends the message to the queue bound to that key.

Topic ​

Topic works like a topic in MQTT: it matches level by level, and it supports the wildcards # and *.

  • * matches exactly one word;
  • # matches zero or more words.

Fanout ​

Every client receives the message.

5. Message acknowledgement ​

Messages sent to RabbitMQ can be lost, so detecting and handling lost messages is necessary. There are three stages:

  • publisher → exchange
  • exchange → queue
  • queue → client

Failures in the first two are usually configuration mistakes in the development environment, so they need little handling — an alert to the developer is enough.

A problem in queue → client, however, is hard to find in a dev environment, so a separate queue is needed to keep the messages that failed to be delivered. That leads to the dead letter queue:
