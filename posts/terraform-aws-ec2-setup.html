Terraform on AWS: Provisioning an EC2 Instance Step by Step ​

My notes from working through a Terraform-on-AWS exercise: installing the CLI, reading a main.tf, applying it, and then cleaning up after myself.

1. Installation ​

Clone the project and install Terraform.

Open cmd as administrator and run echo %PATH% to see which folders Terraform can run from.

It failed to run, so Go has to be installed as well: https://go.dev/dl/.

After installation the environment variables need to be configured.

Open Environment Variables and add Go to PATH.

Click OK, apply the change, and restart cmd.

Installed successfully.

Getting credentials ​

Run aws login to obtain credentials.

As shown above, the last line is the credentials.

2. The Terraform files ​

HashiCorp maintains the Terraform Registry, so providers can be taken from the public registry.

  • The source is written as [hostname (optional)/]namespace/provider.
  • The full form is registry.terraform.io/hashicorp/aws, but since the hostname defaults to registry.terraform.io it can be omitted.
  • If version is left empty, the newest version is selected automatically.
  • required_version is the Terraform version.

The guide hands you a main.tf; here is what each part of it does.

Provider ​

A provider configures the API of a cloud platform, and the provider block is where a provider is configured. There can be several provider blocks, for example to configure more than one provider.

The AWS provider authenticates the same way as the AWS CLI, which needs AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY. There are three ways to authenticate:

  1. Directly in the provider block — highest priority.
  2. Through environment variables, for example in Windows cmd: set AWS_ACCESS_KEY_ID=XXX.
  3. Automatically. Once aws login has been run, the credentials are already on the machine; check them with aws configure list in the cmd session that is logged in to AWS.

Data ​

A data block does not configure anything — it reads from the provider. Everything in it is a query, resolved at run time, so nothing is visible before Terraform runs.

Resource ​

Which arguments a resource takes is decided by the people who wrote the provider (AWS, Azure, ...).

The first line of a resource declares aws_instance "app_server" — the resource type and the local name. Together they form aws_instance.app_server, which resolves to the instance id.

  • ami selects the image.
  • instance_type is hard-coded to t2.micro, which fits inside the AWS free tier.
  • tags sets the name of the EC2 instance.

3. Applying the configuration ​

Format the files the way Terraform recommends:

bash
terraform fmt

If the files do not match the style, they are rewritten.

Initialise the working directory:

bash
terraform init

Validate the configuration:

bash
terraform validate

The configuration is valid.

Terraform applies infrastructure in two steps: it prints an execution plan and waits for approval, then uses the provider to make the changes. That workflow lets you inspect anything unexpected. Run terraform apply — Terraform prints the plan and asks you to confirm.

An error: after a reboot the aws login session is no longer valid. Open cmd again, run aws login, and try once more.

It failed again — aws login only applies to the AWS CLI and the SDKs.

Working around the expiring session ​

Run aws configure export-credentials --format env to get the credentials.

Then put them into environment variables:

powershell
$env:AWS_ACCESS_KEY_ID = "your_access_key"
$env:AWS_SECRET_ACCESS_KEY = "your_secret_key"
$env:AWS_SESSION_TOKEN = "your_session_token"
$env:AWS_DEFAULT_REGION = "us-east-2"

They expire

Be quick about it. Honestly, this authentication dance is a real pain.

Type yes.

Created successfully — AWS even sent an email about it. The new instance can be found in the EC2 console.

State ​

After the write, Terraform creates a terraform.tfstate file that it uses to manage the lifecycle.

bash
terraform state list

…lists the resources Terraform is managing.

4. Changing the configuration ​

Create variables.tf so that values can be changed there instead of inside main.tf.

variables.tf

Creating output.tf as well is recommended, so that more information can be surfaced.

output.tf

Those two values follow the resource in main.tf; to output something else, the values have to be changed.

Back to the point: the resource values in main.tf are hard-coded, so now that variables.tf exists, the resource has to reference the variables instead.

main.tf

This way the values come from the variables.

bash
terraform plan -var instance_type=t2.large

The variable was overridden successfully.

Module ​

A module is a reusable set of configurations that can manage multiple resources and data sources. Ready-made modules live on the Terraform Registry, or you can write your own.

After putting the module into main.tf the editor warns, because terraform init has not been run yet. Run it in the terminal and the warning disappears.

Then add these to the resource:

hcl
vpc_security_group_ids = [module.vpc.default_security_group_id]
subnet_id              = module.vpc.private_subnets[0]

The purpose is to place the EC2 instance in the first private subnet of the new VPC, using the VPC's default security group.

Run terraform init again every time the configuration changes, then run terraform apply.

It succeeded, but public_ip is empty — which is normal, because the instance now sits in a private subnet.

5. Removing everything ​

The resource and the output have to be deleted (or commented out) to remove the EC2 instance; after that, tell Terraform about it with terraform apply.

Then run terraform destroy to remove the working directory state and the resources in the cloud.

To sum up: terraform apply removes the resources you asked it to remove, while terraform destroy tears down everything the configuration created — the local files stay.
